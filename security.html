Security & data handling.

Spikewatch was designed so that the sensitive thing - your prompts, your customers, your code - is never in scope. This page states exactly what the system can see, in plain terms, because the code that backs every claim is public.

Scope

What it can see. What it can never see.

Within scope

  • Hourly token counts per model, from your provider's usage report API.
  • Cost-report figures where the provider exposes them.
  • Estimated dollar totals, computed from token counts and public list prices.
  • A Slack webhook URL you create, so alerts have somewhere to go.

Never in scope

  • Prompts and responses. The usage report API does not contain them, and nothing else is ever requested.
  • Your regular API key. Spikewatch uses a separate, read-only Admin key. It cannot make a single model call.
  • Your customers or end users. No request data passes through Spikewatch - there is no proxy and no SDK.
  • Your codebase. Nothing is installed, imported, or executed in your environment.

The key

A key that can look, and cannot touch.

The only credential Spikewatch holds is an Anthropic Admin API key scoped to usage and cost reports. That scope is enforced by the provider, not by Spikewatch: the key is technically incapable of creating messages, changing settings, or spending money. If it were ever leaked, the worst it could show someone is your usage totals - and you can revoke it in the Anthropic Console in seconds. How the key works →

Read-only by scope

The permission boundary lives at the provider. It doesn't depend on trusting Spikewatch's code - though that code is public too.

Encrypted at rest

On the hosted service, keys are stored encrypted. Self-hosted, your key never leaves GitHub's encrypted secrets in your own repo.

Revocable in seconds

Kill the key in your provider console and every check stops. No offboarding process, no data to retrieve.

Data flow

Three stops. No fourth.

Every hour, the job makes read-only requests to the usage API, runs the detection, and - only if the rule fires - posts one message to your webhook. There is no dashboard database of your history to breach, and the engine itself stores nothing between runs beyond what your provider already keeps.

This website

The checker runs on your device. Watch it if you like.

Nothing uploaded

The live checker at /app/ imports the detection engine into your browser and runs it there. Your pasted usage data never leaves the page - open your network inspector and watch: no request carries it anywhere.

Webhook used once, from your browser

If you test a Slack webhook in the checker, the test message is sent directly from your browser to Slack. The URL is not stored.

Site analytics

These pages use Microsoft Clarity to see which sections get read. It records page interactions on spikewatch.live - it has no access to your provider account, which is exactly why the checker is client-side.

Open by default

The engine, the hourly job, the tests, and every claim on this page: github.com/shantanupatil-debug/spikewatch. If this page and the code ever disagree, the code is right - file an issue.

Plain talk

What this page is not.

Spikewatch is a one-founder product. There is no SOC 2 report to wave at you yet, and inventing badges would be worse than not having them. What exists instead: a read-only permission boundary enforced by the provider, a system with no prompts to leak, and source code you can read end to end before you connect anything. For the data it actually touches - hourly usage totals - that is a stronger position than most dashboards holding your full prompt history.

Verify, then trust

Read the engine. It is short.

The detection core is about a page of code, the hourly job another. Both are commented and tested. If you have found a problem, open an issue on the repo.
